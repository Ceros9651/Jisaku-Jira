# /createPR

引数: `$ARGUMENTS`

今のブランチから `dev` への PR を作る。引数があれば、タイトルと本文を作るときの補足として使う（PBI の番号、注意の節に書くこと、など）。

**コミット・push・PR の作成は、それぞれ AskUserQuestion でユーザーの了承を得てからだけ行う。** 了承が得られなければ、その時点で止める（それまでにしたコミットは残してよい）。

## 1. 前提の確認（読むだけ）

変更を伴う操作の前に、次をすべて確かめる。満たさないものがあれば、何も変えずに理由と次にすべきことを伝えて止める。

1. `git rev-parse --abbrev-ref HEAD` でブランチ名を得る。
   - `dev` / `main` → 「作業用のブランチ（例: `PBI-<番号>`）を切ってから `/createPR` を呼んでください」と伝えて止める。
   - `HEAD`（detached HEAD）→ ブランチに切り替えてから呼ぶよう伝えて止める。
2. `gh auth status` が未ログインなら、`gh auth login` を実行するよう伝えて止める。
3. `git fetch origin dev` のあと、`git status --porcelain` で未コミットの変更を、`git log origin/dev..HEAD --oneline` で `dev` より先のコミットを確かめる。
   - 先のコミットも未コミットの変更も無ければ、PR にする変更が無いと伝えて止める。
4. `gh pr list --head <ブランチ名> --base dev --state open --json number,url` で、開いている PR を確かめる。
   - すでにあれば、新しい PR は作らない。その PR の URL を伝える。
   - `git log origin/<ブランチ名>..HEAD --oneline`（リモートにブランチが無ければ全コミット）で push していないコミットがあれば、push してよいかを AskUserQuestion で確かめ、了承されたときだけ `git push origin <ブランチ名>` する。未コミットの変更があれば先に 2 の手順でコミットする。ここで終わる。

## 2. 未コミットの変更のコミット

未コミットの変更（ステージ済み・未ステージ・追跡していないファイル）があるときだけ行う。

1. 変更されたファイルの一覧を示す。`.env` / `.env.local` など `.env` で始まるファイル（`.env.example` を除く）や、鍵・トークンを含みそうなファイルは対象から外し、外したことを伝える。
2. コミットメッセージの案を示す。リポジトリの慣例に合わせ、`feat:` / `fix:` / `docs:` / `chore:` などの接頭辞＋日本語の要約（「〜する」の形）にする。最後の行は、会話のシステムが指定するコミットの署名（`Co-Authored-By: ...`）にする。
   - 変更の性質が大きく違う（OpenSpec の提案と実装など）なら、分けたコミットの案にしてよい。
3. AskUserQuestion で「コミットする」「直してほしい点を伝える」「やめる」を聞く。
   - 直す点が来たら案を直して再び聞く。
   - 「やめる」なら、コミットも push も PR の作成もせずに止める。
4. 了承されたら、対象のファイルを `git add <ファイル>` で個別に加えてコミットする（`git add -A` は使わない）。フックが失敗したら、内容を伝えて止める。

## 3. タイトルと本文の案

材料は、優先順に次のとおり。

1. このチャットで実装した内容と、実際に実行・確認したこと
2. `git log origin/dev..HEAD` と `git diff --stat origin/dev...HEAD`
3. 差分に含まれる `openspec/changes/<name>/proposal.md`（アーカイブ済みなら `openspec/changes/archive/*-<name>/proposal.md`）
4. `/createPR` の引数

チャットに材料が無い（別のチャットで実装した）ときは 2〜4 から作る。

### タイトル

- ブランチ名が `PBI-<番号>` で始まるときは `PBI-<番号> <変更の要約>`（例: `PBI-6 PBI に受入条件の欄を足す`）。
- それ以外は変更の要約だけ。

### 本文

日本語で、次の構成にする（PR #5 の形）。

```markdown
## 概要

PBI-<番号>: <何を、なぜ変えたか。1〜3 文>
https://ceros9651.github.io/Jisaku-Jira/#PBI-<番号>

## 変更

- <変更点を具体的に。ファイル名・振る舞い・テスト・OpenSpec の change>

## 確認

- <このチャットで実際に実行・確認したこと>

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

- PBI の番号が分からなければ、概要の PBI の行と URL は省く。
- 注意（互換性、デプロイ後のお願いなど）やマージ後に残る作業があれば、「## 確認」の後に節を足す。引数で渡された注意もここに書く。
- 最後の署名行は、会話のシステムが PR の本文の署名として指定するものを使う。
- **「## 確認」には、このチャットで実際に実行・確認したことだけを書く。** 実行していないテスト・型チェック・ビルドを通ったと書かない。何も確認していなければ「このチャットではテスト・ビルドを実行していない（CI で確認する）」のように書く。
- このチャットでテスト・型チェック・ビルド・画面の確認のどれも行っていないときは、案を見せる前に AskUserQuestion で「`npm run typecheck && npm test && npm run build` を実行してから作る」「実行せずに作る」を聞く。実行したら、その結果（失敗ならその内容）を「## 確認」に反映する。失敗したときは、そのまま PR を作るかも聞く。

## 4. 了承と作成

1. 次をすべて示す。
   - ベース: `dev`
   - ヘッド: `<ブランチ名>`
   - PR に入るコミット（`git log origin/dev..HEAD --oneline`）
   - タイトル
   - 本文の全文
2. AskUserQuestion で「作成する」「直してほしい点を伝える」「やめる」を聞く。
   - 直す点が来たら案を直し、再び全文を示して聞く。
   - 「やめる」なら、push も PR の作成もせずに止める。
3. 「作成する」が選ばれたら:
   1. `git push -u origin <ブランチ名>`
   2. 本文をスクラッチパッドの一時ファイルに書き、`gh pr create --base dev --head <ブランチ名> --title "<タイトル>" --body-file <一時ファイル>` を実行する（本文の `` ` `` や `$` が壊れないよう `--body` は使わない）。
   3. 作成された PR の URL を伝える。

## してはならないこと

- PR のベースを `dev` 以外にする。
- force push（`--force` / `--force-with-lease` / `+<ref>`）、他のブランチへの push。
- PR のマージ、レビュアー・ラベルの設定。
- `--no-verify` などでフックや署名を省くこと。
- 了承を得る前のコミット・push・PR の作成。
- push や PR の作成が失敗したとき（リモートが先に進んでいて拒否された、など）に、別の方法で回避すること。エラーの内容と原因をそのまま伝えて止める。
